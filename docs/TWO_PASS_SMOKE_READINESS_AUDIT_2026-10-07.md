## C. 第二轮：独立重建 prompt，并检查能否承接下一阶段

第二轮没有只相信完成标记：从每轮开始时的历史快照、反馈和当前代码，重新生成全部 48 个 builder prompt；模型接口在调用前被本地捕获，外部 SDK 被禁止构造。48 个 prompt 与实际发送版本逐字一致。ACL 与轮初可见工具集合一致，未发现同轮／未来工具泄漏。

随后独立检查原计划阶段 B：四组各 8 agents × 12 轮、seed 2001、384 次构建 + 48 次 solver。发现以下三个开跑阻碍。

### P1-1：下一阶段入口和预算计算还没有实现

- **确认事实：**将阶段 B 参数交给当前只读配置解析器，直接拒绝：`n_agents differs from the fixed smoke contract`。
- 当前 [agentport_config.py](../boidsnet/runner/agentport_config.py) 的 110–121 行将当前网关入口限定为 4 agents、3 轮、96 次请求及单次运行最高 8 元；[sac_pilot.py](../boidsnet/runner/sac_pilot.py) 的 61–70 行另有限定 seed 1001、最多 3 轮。
- 实际执行还在 `sac_pilot.py` 的 285–292 行写死组序、seed 与输出命名。它不能通过只修改 JSON 就成为计划中的阶段 B。
- 更关键的是 `agentport_config.py` 的 81–85 行最坏费用按 **96 次调用**写死。只删参数限制，不把调用量、预算、组序、seed 和审核绑定一起参数化，会留下错误的启动前预算保证。
- 这不是 run-12 的 bug，而是下一阶段尚未实现的入口。不能用旧 batch 入口绕过保护。

**预算差异：**按当前本地 3.2/8.4 CNY 每百万输入／输出的记账参数，输入 16,000 字节加 512 framing 预留、输出上限 builder 4,000／solver 1,500，阶段 B 零重试的最坏预留为 **36.3333888 元**；如沿用旧计划最多 480 请求并将额外 48 次按 builder 预留，则为 **40.4824320 元**。旧计划的 35 元限额不能原样沿用。上述是保守本地预留，不是预测实际扣费，也不是已验证的供应商报价。

### P1-2：后期工具目录存在已复现的输入容量问题

- 使用当前真实工具的元数据复制成 8 agents × 11 个历史轮次、88 个唯一工具 ID 的**合成容量 fixture**，调用现有第 12 轮 prompt 构造逻辑；不运行生成代码，不请求模型，不改原始工具。
- 四组均在模型调用前报错：`shared SAC prompt exceeds input cap; no task or evidence module was dropped`。
- [society.py](../boidsnet/runner/society.py) 的 145–164 行已尝试同步缩减规则代码摘录和目录描述；缩到下限后仍无法装入 16,000 字节。这保持了不随意丢任务／证据的原则，但尚不能覆盖该后期容量。
- Solver 也按 [utility.py](../boidsnet/runner/utility.py) 的 338–348 行列出整个冻结库，没有对应的预算感知压缩。合成目录 40 项为 12,888 字节，60 项为 18,644 字节，88 项为 26,384 字节；后两者超过当前上限，会被 [local_budget.py](../boidsnet/runner/local_budget.py) 的 104–106 行拒绝。
- **边界：**这证明现有实现有可复现的容量反例；不证明下一次真实运行必定保留 60/88 个工具，也不是已经做过 12 轮真实实验。不能据此预测具体真实失败轮次。

需要在花钱跑构建之前修复完整目录的表示／输入预算，并覆盖目标后期规模；任何输入上限调整必须同时重算单请求与全阶段预留。不能为了塞进 prompt 悄悄只给某组删工具、删任务或删规则证据。

### P1-3：原计划要求的机制分析尚未接入完整流程

- 计划阶段 A 已明确要求：在真实 smoke 产物上运行行为重复、独立可靠覆盖、M_cross 分类、逐轮覆盖；并非这次临时追加的防御性实验。
- 当前 `sac_pilot.py` 的 303–320 行完成构建与 `score_society` 后即输出完成报告；没有这些分析的必经入口。
- 代码检索和现有审计文档均确认，实验 2–4 的独立分析管线、importer-specific 功能边消融与汇总还未实现。见 [STRICT_REAUDIT_2026-10-06.md](STRICT_REAUDIT_2026-10-06.md) 第 47 行和 [SAC_DEEPSEEK_REVIEW.md](SAC_DEEPSEEK_REVIEW.md) 第 103 行。
- 已有 primitive 开发验证用于反馈／冻结，不能冒充计划中独立的可靠覆盖评估。计划另指定分析 probe 区间 40,000–49,999；本轮没有将旧开发评分重新标成这些新测量。
- 已有静态跨 agent import 计数也不能替代 M_cross：还须区分 importer-specific 的有效功能依赖、仅结构性报错、未知分类，以及空库／无候选边的定义。

这些主要是**复用已有工具和日志的本地分析实现**，无需为了补指标新增模型、增加 seeds 或重新生成一批工具。

## D. 机制与科研结论：通过了什么，还没证明什么

| 逻辑环节 | 当前证据 | 判断 |
| --- | --- | --- |
| 四组干预按开关发送 | 48 个 prompt 精确重建；关闭规则未触发 | 已验证当前输入范围 |
| Separation 有机会生效 | 100、111 各 8 次后续机会中触发 2 次 | 有真实指令发送；不等于模型行为已改变 |
| Alignment 使用优质／被采用样例 | 全部 48 次 builder 为 TARGET NONE；两启用组的 16 次 A 都走 fallback | fallback 路径已出现，非 fallback 分支未被真实 smoke 覆盖 |
| 跨 agent 工具依赖形成 | 48 次构建均无跨 agent 静态导入 | 没有真实依赖样本；solver 多工具组合不是这个证据 |
| 减少冗余、增加可靠覆盖 | 独立分析管线尚未完成 | 未测量，不能推断 |
| 工具库可以被调用并正确评分 | 48 条评分重放一致，包含两步和三步成功组合 | 工程正面证据 |
| Separation 改善群体效用 | 每组仅一个 3 轮开发社会，合并成功率 12.5% | 无明确科学结论；不是支持也不是推翻原 idea |

TARGET NONE 是允许的输出，不自动等于接口 bug；因此也不能把 A fallback 当成有质量／采用信号的 alignment 已验收。没有跨 agent 边也不允许人为补造依赖或不断重跑直到出现。

当前低分可能同时涉及可调用能力不足及 solver 参数／组合错误；已有结果不足以确定各原因占比。不能仅靠扩规模或把所有模型错误当系统 bug 修掉，来保证 separation 得到正结果。

这些限制不要求额外多模型／多 seed 稳健性实验。最小处理是检查缺失分支的契约、用明确标注的人工 fixture 测分类，再在既有真实产物上运行分析；真实无对象分支如实报告，不能把人工正例称成模型产生的研究证据。

另有文档漂移：旧配置／说明仍混有此前模型入口、预算与早期未验证状态。最新运行报告应与新阶段配置对齐，避免继续把旧价格、旧入口或“核心完成”当成全计划可直接开跑。
